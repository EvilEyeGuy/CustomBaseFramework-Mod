Dungeon levels: development reference

Modding

The current local framework contains a dungeon planner and stairs between maps. Its example content lives in the separate Custom Base Framework - Dungeons (Dev) mod, whose metadata marks it as development content, not a release. The fields below describe that local implementation; their presence does not mean the base mod supplies a finished set of playable dungeons.

For regular towns and camps, use Settlement plans. Dungeon plans use the same SettlementPlanDef, with kind set to Dungeon and an ordered levels list instead of the usual town, suburb and countryside wards. The old DungeonProfileDef is not the entry point for this workflow.

Build one level before adding another

Start with a few room pieces in one level's districts. Each district has the same category or piece requests used by settlement districts. The level's layout selects Corridors, Chambers or Cave; a district can supply its own layout override. These choices control the intended room arrangement, so compare their generated layouts with the same room set.

The first level uses the surface map. Lower levels are separate pocket maps generated through the stairs. A level's positive mapSize sets the size of its lower map; 0 lets CBF estimate it from the requested rooms. Set the surface map size on the plan itself, not on the first level.

Connect two levels

This is the levels fragment of a two-level plan. The room and stair names below come from the development content and require that content and Medieval Overhaul. It is not a standalone definition:

<levels>
  <li>
    <name>Upper</name>
    <layout>Corridors</layout>
    <stairsDown>
      <li><piece>CBF_MO_Dungeon_Stairs_Down_A</piece></li>
    </stairsDown>
    <districts>
      <li>
        <name>Lair</name>
        <entries>
          <li><tag>CBF_Dungeon_CultistDormitory</tag><count>1~2</count></li>
        </entries>
      </li>
    </districts>
  </li>
  <li>
    <name>Lower</name>
    <entrance>
      <li><piece>CBF_MO_Dungeon_Stairs_Up_A</piece></li>
    </entrance>
    <districts>
      <li>
        <name>Sanctum</name>
        <entries>
          <li><piece>CBF_MO_Dungeon_RitualCircle_Upscale_A</piece><count>1</count></li>
        </entries>
      </li>
    </districts>
  </li>
</levels>

stairsDown adds the stair-room requests leading to the next level. Every level except the last needs this list. On lower levels, entrance adds the rooms containing the way back up. The current conversion adds one room request per list entry; these lists are not a single weighted choice of one stair room, and their count field is not used as the room count.

The stair pieces also need Connect anchors named StairsDown or StairsUp, respectively. These mark the portal position inside the room. A normal door, a Socket anchor or an entry in stairsDown alone does not create the portal. The required portal and map-generator definitions are part of the development setup.

Use the complete CBF_Plan_Dungeon_Levels_Test.xml in the development mod as a starting point. Test travelling down and back up in game before adding more levels. A map preview cannot establish that the portals and quest setup work together.

Fields that are not yet connected to generation

Several settings are stored and exposed by the editor but are not passed through the current framework-to-planner conversion:

  • Level corridors, caveWidth, caveShare and secretChance.
  • The plan's spread list for distributing requests between levels.
  • The legend's socketType and socketWidth settings.

Do not rely on these fields to change the generated result in this version. Put room requests directly in each level's districts. In particular, a spread entry is not a substitute for those requests. This distinction matters when patching: a value can load correctly and appear in the editor without affecting the map.

The reference pages describe the available structure: DungeonLevel, SpreadEntry, DistrictSpec and LegendEntry. The behaviours above were checked against the local source; this documentation pass did not run an in-game dungeon test.
