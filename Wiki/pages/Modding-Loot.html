Modding: loot, object lists, containers and crops

This page covers the XML side of loot in Custom Base Framework (CBF). The editor side is described on Loot. Every field is listed on the field reference pages linked at the end.

How loot gets into a settlement

Loot always starts at an anchor in a piece.

  1. A piece has a legend entry with anchorKind Fill or Object.
  2. The anchor names an object list in objects and, for fill anchors, a loot table in lootTable.
  3. CBF picks one structure from the object list that fits the anchor area and places it.
  4. The loot table is rolled and the result goes into that structure or onto it.

A real anchor from a Medieval Overhaul piece:

```xml

  • 4FassFillCBF_MO_FassCBF_MO_Loot_Speisekammer
  • 5RegalFillCBF_MO_Wappenregaltrue

    • ```

    Node Meaning
    anchorKind Fill places a structure and loot. Object places a structure only, the anchor's lootTable is ignored.
    objects defName of a LootBuildingCategoryDef.
    lootTable defName of a LootTableDef. Used for every structure of the list unless a member brings its own table.
    lootFremd The anchor places the structure and leaves filling to the mod that owns it. The anchor's lootTable is ignored.
    chance Chance that the anchor is used at all. If it fails, the anchor cells are cleared, unless obenauf is set.
    obenauf The structure goes on top of what is already there. The cells are not cleared.

    A fill anchor with neither object list nor loot table stays empty and logs a warning. A fill anchor with a loot table but no object list drops the loot loose on the floor near the anchor.

    Pieces can also have content zones (contentZones, see ContentZoneSpec). They use the same object lists and loot tables. A zone without its own lootTable falls back to the lootTable of the settlement's BudgetEntry for that category.

    Object lists

    Node: <CustomBaseFramework.LootBuildingCategoryDef>. An object list names the structures an anchor may place.

    xml <CustomBaseFramework.LootBuildingCategoryDef MayRequire="DankPyon.Medieval.Overhaul"> <defName>CBF_MO_Fass</defName> <members> <li>DankPyon_HideoutRusticBarrelClosed</li> <li>DankPyon_HideoutCrate1x1c</li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    A member can be a plain defName, as above, or a block with more nodes:

    xml <CustomBaseFramework.LootBuildingCategoryDef MayRequire="DankPyon.Medieval.Overhaul"> <defName>CBF_MO_Waffenregal</defName> <members> <li><thing>DankPyon_HideoutRackSword</thing><fremd>true</fremd></li> <li><thing>DankPyon_HideoutRackSpear</thing><fremd>true</fremd></li> <li><thing>DankPyon_HideoutRackMixed</thing><fremd>true</fremd></li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    Member nodes

    Node Meaning
    thing defName of the structure.
    lootTable A loot table for this member only. It replaces the anchor's table. If the table does not exist, the anchor's table is used and a warning is logged.
    leer What it becomes once emptied. On a shelf or other open structure, this building takes its place. On a shell (see below), only its picture is used. Must have the same footprint as thing, otherwise a warning is logged and the swap does not happen.
    bleibt The structure itself is placed and stays as it is. Loot lies visibly on it or goes into it. offen is read as the same node.
    fremd CBF places the structure and does nothing else. Loot, occupants and the empty look come from the mod that owns it.

    A shipped example of bleibt:

    xml <CustomBaseFramework.LootBuildingCategoryDef MayRequire="DankPyon.Medieval.Overhaul"> <defName>CBF_MO_Schreibzeug</defName> <members> <li><thing>DankPyon_OnTop_Scribe_Book</thing><bleibt>true</bleibt></li> <li><thing>DankPyon_OnTop_Scribe_ScrollAndInkwell</thing><bleibt>true</bleibt></li> <li><thing>DankPyon_OnTop_Scribe_StackPaper</thing><bleibt>true</bleibt></li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    What gets placed

    What CBF places depends on the kind of building and the member flags.

    • CBF container (thingClass is CustomBaseFramework.Building_Beutebehaelter): placed as is. It gets the loot table and rolls it when it spawns.
    • Other container (any Building_Casket, for example a Medieval Overhaul lootable chest) without bleibt or fremd: CBF places a shell of the same size instead. The shell looks like the original, takes its label and description, and holds the loot inside until it is opened. If the member has leer, the shell shows that building's picture once opened.
    • Storage (a shelf, Building_Storage): placed as is. The loot lies on its cells, respecting the shelf's storage filter and items per cell.
    • Anything else, for example a table: placed as is. The loot lies on its cells.
    • With fremd, or on an anchor with lootFremd, none of the above applies. The structure is placed and left alone.

    Loot on a structure's cells takes the cell with the fewest items. A shelf allows its maxItemsInCell, anything else one stack per cell. When every cell is full, the rest of that item is not created. Items a shelf does not accept go onto free floor within 4 cells of the anchor, as does loot that does not fit into a container.

    What it becomes when emptied

    For structures that hold loot on their cells, CBF checks every 250 ticks whether the loot is gone.

    • With leer: the structure is replaced by the leer building, same position and rotation.
    • Without leer, on a shelf: the shelf stays.
    • Without leer, on anything else: the structure vanishes.
    • With bleibt or fremd: nothing is checked, the structure stays.
    • Structures owned by the player, or on a map owned by the player, are never swapped or removed.

    CBF containers handle this themselves, see Containers.

    Pawn inside

    An object list can hide someone in its containers. This only works for buildings with an inside (caskets and CBF containers), not on shelves.

    xml <CustomBaseFramework.LootBuildingCategoryDef> <defName>MyMod_TrappedChest</defName> <members> <li>MyMod_Chest</li> </members> <pawnList>MyMod_ChestAnimals</pawnList> <pawnChance>0.15</pawnChance> <pawnCount>1</pawnCount> <pawnFeindlich>true</pawnFeindlich> </CustomBaseFramework.LootBuildingCategoryDef>

    Node Meaning
    pawnList defName of a PawnListDef.
    pawnChance Chance per container. Default 0, so nobody is inside unless set.
    pawnCount How many, as a range.
    pawnFeindlich The pawn attacks once the container is opened. Animals go manhunter, people go berserk. A pawn of a faction hostile to the player fights for its faction instead. Handled by CBF containers and shells.
    pawnFraktion FactionDef of the occupant. Without it, a non-hostile person joins the settlement's faction.

    In a CBF container, a hostile occupant acts as a guard. Opening the container first releases the guard. The container cannot be searched while the guard is alive and outside.

    Kind

    art takes Fuellen (default) or Leer. With Leer the structures are placed without loot and without occupants, and Medieval Overhaul lootables do not fill themselves either.

    Object size and anchor area

    The anchor area is the set of cells drawn with the anchor symbol. Only members that fit into the free cells of that area can be picked. A member may be placed turned by 90 degrees if its rotatable is true.

    • Among the members that fit, the pick is weighted by footprint. A 2x1 shelf is twice as likely as a 1x1 crate.
    • At an anchor, CBF places the structure as close to the middle of the area as it fits.
    • Rotation and stuff come from the placeholder building drawn under the anchor, if there is one and the stuff fits.
    • Water cells never count as free.
    • If no member fits: with a loot table, the loot is dropped loose near the anchor. Without one, the drawn placeholder stays and a warning is logged.

    In dev mode, CBF warns when only one member of a list ever fits an area, because then the same structure always appears.

    Other mods

    Use MayRequire on the list or on a member so the XML loads without that mod.

    xml <CustomBaseFramework.LootBuildingCategoryDef> <defName>CBF_Vanilla_Schildgenerator_Hoch</defName> <members> <li MayRequire="Ludeon.RimWorld.Royalty"><thing>ShieldGeneratorMortar</thing><bleibt>true</bleibt></li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    A member whose thing does not exist is skipped silently. If no member is left, the list is empty and every anchor that uses it is cleared and stays empty. If the list itself does not exist, the anchor stays empty and a warning is logged.

    Loot tables

    Node: <CustomBaseFramework.LootTableDef>. A loot table decides what comes out. Entries can be a single item, another table or a whole thing category.

    A table of tables:

    xml <CustomBaseFramework.LootTableDef> <defName>CBF_MO_Loot_Wohnhaus</defName> <label>Wohnhaus</label> <rolls>2~4</rolls> <uniqueEntries>true</uniqueEntries> <emptyFallback>CBF_MO_Loot_Minimal</emptyFallback> <entries> <li><weight>20</weight><table>CBF_MO_Ware_Brot</table></li> <li><weight>16</weight><table>CBF_MO_Ware_Kaese</table></li> <li><weight>12</weight><table>CBF_MO_Ware_Textil</table></li> <li><weight>8</weight><table>CBF_MO_Ware_Wein</table></li> </entries> </CustomBaseFramework.LootTableDef>

    A table of items:

    xml <CustomBaseFramework.LootTableDef> <defName>CBF_Vanilla_Ware_Gewand</defName> <label>Gewand</label> <rolls>1~2</rolls> <entries> <li><weight>20</weight><thing>Apparel_BasicShirt</thing><count>1~3</count><quality>Awful~Good</quality><hitPoints>0.4~0.9</hitPoints><onMissing>Skip</onMissing></li> <li><weight>12</weight><thing>Apparel_Jacket</thing><count>1~2</count><quality>Awful~Good</quality><hitPoints>0.4~0.9</hitPoints><onMissing>Skip</onMissing></li> <li MayRequire="Ludeon.RimWorld.Royalty"><weight>2</weight><thing>Apparel_Corset</thing><count>1</count><quality>Normal~Excellent</quality><onMissing>Skip</onMissing></li> </entries> </CustomBaseFramework.LootTableDef>

    Table nodes

    Node Meaning
    rolls How many entries are drawn from entries. Default 1~3.
    rollChance Chance that the draw happens at all. One check for the whole draw, not per roll. If it fails, only always entries come. Default 1.
    uniqueEntries Each entry can be drawn at most once per draw. Default false.
    maxEntriesPerResolve Drawing stops once this many picks have been made. Default 16.
    always Entries that are taken every time, each after its own chance check. They do not use a draw.
    entries Entries drawn by weight.
    emptyFallback Another table, rolled if this one produced nothing. It may not point to itself.

    Nested tables and fallbacks go at most 4 levels deep. Deeper levels produce nothing.

    Entry kinds

    Each entry sets exactly one of thing, table or category. An entry in entries with none of them is a config error. If more than one is set, table wins over category, and category wins over thing.

    Kind Node What happens
    Item thing That ThingDef.
    Table table The named table is rolled tableRolls times (default 1) and everything it gives is added.
    Category category A ThingCategoryDef. One thing from the category and its subcategories is picked, weighted by the thing's generateCommonality.

    A category entry, written for this page:

    ```xml

  • 4 Drugs Medieval 5~60 1~3

    • ```

    For categories, only things the game allows in random item sets are used. maxTechLevel drops things above that tech level. value drops things whose base market value lies outside the range; the default 0~0 means no limit. If nothing is left, the entry gives nothing. Things made from stuff get a random fitting stuff.

    Entry nodes

    Node Meaning
    weight Weight against the other entries in entries. Default 1. An entry with weight 0 is never drawn.
    chance Only used in always: the chance that the entry is taken. Default 1.
    count Stack count as a range. Counts above the stack limit are split into several stacks.
    quality Quality range, for example Poor~Good. Picked evenly within the range. Only for things that have quality. Default Awful~Legendary.
    hitPoints Condition as a fraction of max hit points, for example 0.5~1.0. Default 1~1.
    stuff Stuff for a thing made from stuff. If it is missing or not a stuff, the thing's default stuff is used.
    maxTechLevel Category entries only, see above.
    value Category entries only, see above.
    tableRolls Table entries only, see above.
    weightOverWealth A curve over the wealth of the player's home map. The weight is multiplied by it.
    requiresAnyMod A list of packageIds. The entry is only used if at least one of them is active.
    onMissing What happens if thing does not exist: Skip, Fallback or Silver. Default Skip.
    fallbackThings Used with onMissing Fallback. The first one that exists replaces thing.

    The fields depthRange, weightOverDepth, countOverDepth and rollsOverDepth read a depth. Settlements always have depth 0. An entry with depthRange starting above 0 never appears, and CBF logs a warning for it.

    When a mod is missing

    There are three ways to handle things from other mods.

    1. MayRequire on the li. The entry is not loaded at all. This is what the shipped tables use.
    2. requiresAnyMod. The entry loads but is ignored unless one of the mods is active.
    3. onMissing for a thing that does not exist:
    4. Skip: the entry is dropped and a warning is logged once.
    5. Fallback: the first existing defName from fallbackThings is used. If none exists, the entry is dropped.
    6. Silver: silver is used instead, with the entry's count.

    ```xml

  • 6 MyMod_Candle 2~5 Fallback
  • DankPyon_Candle
  • Candle

    • ```

    A table or category entry that points to something that does not exist is dropped with a warning. If no entry of a table is usable, the table stays empty and CBF logs it. An anchor that names an empty table places its structure without loot.

    Containers

    A CBF container is a building that holds loot inside, looks different once searched, and can turn into another building or vanish. Use it when a plain shelf is not enough.

    CBF ships an abstract base, CBF_BeutebehaelterBase, in Defs/CustomBaseFramework/ThingDefs/CBF_Beutebehaelter.xml. It sets thingClass to CustomBaseFramework.Building_Beutebehaelter, the contents tab and the usual building values. Inherit from it and add a size, a graphic and the extension.

    xml <ThingDef ParentName="CBF_BeutebehaelterBase"> <defName>CBF_Behaelter_Regal</defName> <label>stocked shelf</label> <description>A shelf someone left behind, still holding what its owner kept there. Once emptied, it is just a shelf again.</description> <size>(2,1)</size> <graphicData> <texPath>Things/Building/Furniture/Shelf</texPath> <graphicClass>Graphic_Multi</graphicClass> <drawSize>(3,2)</drawSize> </graphicData> <modExtensions> <li Class="CustomBaseFramework.BeutebehaelterExtension"> <leerGebaeude>Shelf</leerGebaeude> </li> </modExtensions> </ThingDef>

    Inheritance only works from a mod that loads after CBF. Otherwise copy the base into your own XML.

    Extension nodes

    CustomBaseFramework.BeutebehaelterExtension:

    Node Meaning
    leerGrafik A GraphicData shown once the container has been searched. It stays the same container.
    leerGebaeude A ThingDef that replaces the container once searched. Needs the same footprint, otherwise the container stays and a warning is logged.
    zerstoerenWennLeer The container vanishes once searched, leaving nothing behind.
    suchklang A SoundDef played when it is opened.
    sucheffekt A FleckDef shown when it is opened.
    effektgroesse Size of that fleck. Default 1.5.

    leerGebaeude and zerstoerenWennLeer exclude each other; setting both is a config error.

    Empty picture only:

    ```xml

  • Things/Building/Ruin/RuinedShelf Graphic_Multi (2.75,2.75)

    • ```

    How it behaves

    • The picture changes when the container is opened, not when it runs out of items.
    • The loot table comes from the anchor or the member, never from the container def. A container placed by hand stays empty. In dev mode with god mode, a gizmo lets you fill it from any table for testing.
    • The contents are rolled once, when the container spawns.
    • A shell takes its empty picture from the member's leer building, or else from an empty graphic declared in the original building's own mod extension. A shell never turns into another building.
    • A container of your own takes its empty picture from leerGrafik.

    Shelves with visible loot

    To show loot lying on a vanilla or modded shelf, do not use a CBF container. Put the shelf in an object list. CBF places the shelf itself and lays the items on its cells. When the items are gone, the shelf stays, or turns into the member's leer building.

    xml <CustomBaseFramework.LootBuildingCategoryDef> <defName>CBF_VFEM2_Regal</defName> <members> <li>Shelf</li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    A mod's own self-filling shelf is marked fremd, so CBF does not touch its contents:

    xml <CustomBaseFramework.LootBuildingCategoryDef> <defName>CBF_VFEM2_Autoregal</defName> <members> <li><thing>VFEM2_AutofillShelf</thing><fremd>true</fremd></li> </members> </CustomBaseFramework.LootBuildingCategoryDef>

    Medieval Overhaul lootables

    Medieval Overhaul lootables fill themselves when they spawn. CBF blocks that while it places one with a CBF loot table, and on lists of kind Leer. With fremd, or on an anchor with lootFremd, the lootable keeps its own loot.

    Crop lists

    Node: <CustomBaseFramework.CropListDef>. A crop list is a weighted list of plants for fields and pens. CBF ships none, so this example is written for this page.

    xml <CustomBaseFramework.CropListDef> <defName>MyMod_Crops_Grain</defName> <label>grain</label> <plants> <li><plant>Plant_Rice</plant><weight>3</weight></li> <li><plant>Plant_Corn</plant><weight>2</weight></li> <li><plant>Plant_Potato</plant></li> </plants> </CustomBaseFramework.CropListDef>

    Node Meaning
    plant defName of a plant. Entries that do not exist or are not plants are skipped with a warning.
    weight Weight against the other plants. Default 1. A weight of 0 or less is a config error and the entry is skipped.

    A list without plants is a config error.

    A field or pen names the list in crops. Fields sit in fields of the settlement or of a district, pens in pens.

    ```xml

  • Acker 1~2 MyMod_Crops_Grain
  • Plant_Rice

    • ```

    If crops names a list that exists and has at least one usable plant, the list is used and plants is ignored. If the list does not exist or has no usable plant, the field falls back to plants, and each of them is equally likely.

    Tips

    • Build small tables of goods and combine them in larger tables with table entries. The shipped tables work this way.
    • Give large tables an emptyFallback, so a structure is never empty just because a roll failed.
    • Use MayRequire on every entry and member from another mod. A list whose members are all missing clears its anchors.
    • Make anchor areas the size of the structures you want. If only one member fits, the same structure always appears.
    • Draw a placeholder building under each anchor. It sets the rotation and stuff of what is placed.
    • Mark a mod's own lootables fremd if their author's loot should stay. Leave the flag off to use your own table.
    • Use the Sample button in the Loot tab to roll a table before testing in game.
