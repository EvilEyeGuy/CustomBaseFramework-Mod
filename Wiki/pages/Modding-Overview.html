Modding overview

This page is for modders who write XML for Custom Base Framework (CBF) by hand or want to know what the editor writes. It covers the folder layout of a content mod, how the defs connect, and the def types that have no page of their own in the guide: wall profiles, styles, ruins, map steps, buildability rules, help texts and dungeon profiles. The last sections explain how CBF takes over faction bases and draws world icons.

Every field is listed in the Field reference. This page shows how the fields are used.

Your own content mod

A content mod for CBF is a normal RimWorld mod. It needs no C# and no patches.

Folder layout

MyCBFContent/ About/ About.xml LoadFolders.xml 1.6/ Defs/ CustomBaseFramework/ CustomBaseDefs/ Buildings/ WallParts/ LootDefs/ PawnKinds/ PlanDefs/ WallProfileDefs/ Mods/ MedievalOverhaul/ Defs/ CustomBaseFramework/ Textures/ World/ WorldObjects/ CBF/ MyTown.png

Only About/About.xml and one Defs folder are required. The subfolder names under Defs are a convention. RimWorld reads every XML file under Defs, whatever the folder is called.

About.xml

The mod depends on CBF and loads after it:

```xml

My CBF Content Me Me.MyCBFContent

  • 1.6
  • EvilEyeGuy.CustomBaseFramework Custom Base Framework
  • EvilEyeGuy.CustomBaseFramework
    •  Content for Custom Base Framework. ```

    loadAfter matters. A def can only inherit with ParentName from a parent in a mod that loads earlier. CBF's abstract parents, such as CBF_Ruin_Basis, are only usable when your mod loads after CBF.

    LoadFolders.xml for other mods

    Content that needs another mod can go into a subfolder that only loads when that mod is active. CBF does this for Medieval Overhaul and Vanilla Factions Expanded - Medieval 2:

    ```xml

  • /
  • 1.6
  • 1.6/Mods/MedievalOverhaul
  • 1.6/Mods/VFEMedieval2
    • ```

    / loads Textures and Languages from the mod root. 1.6 loads 1.6/Defs and 1.6/Patches. Each conditional line loads its own Defs and Languages folders.

    MayRequire

    For single defs or single list entries, RimWorld's MayRequire attribute is enough. On a def node it skips the whole def when the mod is missing. On a list item it skips only that item, for example a member of an object list:

    ```xml

  • DankPyon_RusticShelf

  • Shelf

    • ```

    See Modding-Settlements for MayRequire on settlement types.

    World icons

    World map icons go into Textures/World/WorldObjects/CBF/ of your mod. A settlement type names one in worldTexture. The editor lists every texture in that folder from all active mods. See World icons below.

    What the editor writes for you

    The in-game editor handles most of this. See Getting started.

    • New mod creates the mod in your Mods folder with About/About.xml (dependency on CBF, loadAfter CBF) and the folders 1.6/Defs/CustomBaseFramework/CustomBaseDefs/Buildings, .../WallParts, .../DungeonRooms, 1.6/Defs/CustomBaseFramework/Layouts, 1.6/Defs/CustomBaseFramework/LootDefs and 1.6/Patches.
    • When you save content that uses other mods, the editor adds those mods to About.xml.
    • When it saves a settlement type, it writes MayRequire on the def node for the mods the type needs.
    • If your mod already has a LoadFolders.xml with IfModActive lines, a new settlement type that needs one of those mods is saved into that mod's folder.

    The editor does not write LoadFolders.xml and does not copy world icon images. Add those by hand.

    How the defs connect

    SettlementPlanDef (settlement type) worldTexture ............ world icon styles .................. StyleDef -> WallProfileDef techLevels, factionTags . which factions use it wards (Stadtteil) ....... rings from the middle outwards walls, gatehouses ..... wall pieces for this ring districts ............. building programme of the ring categories .......... PieceCategoryDef pieces ............ PieceDef anchors ......... object lists, LootTableDef, PawnListDef

    • Settlement types, wards and districts: Modding-Settlements
    • Pieces, categories and anchors: Modding-Pieces
    • Loot tables and loot containers: Modding-Loot
    • Pawn lists, garrisons and unit swap: Modding-Pawns
    • Quest sites and ruins in quests: Modding-Quests

    The rest of this page covers the defs on the side of that tree.

    Wall profiles

    A WallProfileDef describes a wall ring as a cross section. Each segment is a piece one cell wide or one cell high. The generator builds the wall line from these segments. A profile can also name a tower and a gatehouse piece.

    Example

    From CBF's Medieval Overhaul folder, labels translated:

    ```xml WallProfile_Stein_3

    3

  • TownWall
  • TownWall
  • TownWall
  • TownWall_Scharte
    • Tower CBF_MO_GateHouse_Small West

    WallProfile_Palisade_1

    1

  • Palisade
    • PalisadeTower ```

    Nodes

    Node Meaning
    style The style this profile belongs to. Used to find a profile for a settlement type.
    depth Thickness of the wall ring in cells. Must be 1, 3 or 5. Default 3.
    segments PieceDef names of the cross sections. Each piece must be 1 cell wide or 1 cell high, otherwise it is skipped with a warning. A segment shorter than depth leaves the missing columns empty.
    tower PieceDef for towers on the wall. It sits on the centre line of the wall, so it must be square with an odd size. Otherwise it is ignored and the generator builds its own round tower.
    gatehouse PieceDef placed with its centre on each gate. Both sides must be odd. Otherwise it is ignored and a plain gate is built.
    gatehouseOutward The side of the drawn gatehouse piece that faces out of the settlement: North, East, South or West. Default South.
    outwardIsLow Default orientation of segments. true means the south end of a vertical strip, or the west end of a horizontal strip, faces outwards. A segment piece that defines its outer side itself overrides this. Default true.
    usable Set false to switch the profile off. CBF also sets it to false when no segment is valid.

    A profile needs at least one segment, otherwise the def reports a config error.

    How a profile is chosen

    1. The settlement type's styles are tried in order. For each style its fallback chain is walked. The first usable profile with that style and the wanted depth wins.
    2. If none matches, the first usable profile with the wanted depth is taken. A warning is logged, and the material then comes from that profile's style.
    3. If no profile has that depth, the one with the nearest depth is taken. Standard wall fills the remaining columns.

    A settlement type or a ward can also list its own wall pieces in walls. These replace the profile's segments. Tower, gatehouse and orientation still come from the chosen profile. See Modding-Settlements.

    Styles

    StyleDef

    A style is only a name with an optional fallback:

    ```xml Standard

    Rustical Standard ```

    fallback is used when nothing is found for this style. The chain may not loop and may not be deeper than 16 steps.

    What a style decides today

    A style only picks the wall profile of a settlement type. It does not restrict which pieces are built, and it has nothing to do with materials.

    Which factions use a settlement type is decided by factionTags and techLevels on the SettlementPlanDef, not by the style. See How CBF takes over faction bases.

    A settlement type lists its styles in order:

    ```xml

  • Rustical

  • Standard

    • ```

    The older single field style still loads. If styles is empty, style is used as its only entry.

    Material lists

    A MaterialListDef decides what the generator uses for the parts it builds itself: walls, doors, gates, fences, roads, bridges, roofs and so on. Every settlement type must name one in materialList. There is no hidden default: without a usable list the settlement type is not built. The editor has its own part for them, see Material lists.

    Trimmed from the shipped base list:

    xml <CustomBaseFramework.MaterialListDef> <defName>CBF_Materialliste_Basis</defName> <label>base</label> <roles> <li> <role>WALL</role> <criticality>Critical</criticality> <chain> <li MayRequire="DankPyon.Medieval.Overhaul">DankPyon_CastleWall</li> <li>Wall</li> </chain> <stuffChain><li>MapStone</li><li>BlocksGranite</li><li>WoodLog</li></stuffChain> <tagSearch>AnyWall</tagSearch> </li> <li> <role>BRIDGE</role> <terrainChain><li>Bridge</li></terrainChain> </li> </roles> </CustomBaseFramework.MaterialListDef>

    A list for your own mod usually inherits from the base list and only overrides what differs. This example is not shipped:

    xml <CustomBaseFramework.MaterialListDef> <defName>MyMod_Materials</defName> <label>my mod</label> <parent>CBF_Materialliste_Basis</parent> <roles> <li> <role>DOOR</role> <fuer><li>Wall_Pallisade</li><li>CBF_MO_Palisadenturm_A</li></fuer> <chain><li>DankPyon_RusticDoor</li></chain> <stuffChain><li>WoodLog</li></stuffChain> </li> <li> <role>FLOOR_ROAD</role> <stadtteil>Umland</stadtteil> <terrainChain><li>PackedDirt</li></terrainChain> </li> </roles> </CustomBaseFramework.MaterialListDef>

    Node What it does
    parent Another material list. Roles not defined here are taken from the parent.
    roles One entry per role and condition.
    role The role name, such as WALL, DOOR, GATE, FENCE, FLOOR_ROAD, BRIDGE, ROOF.
    criticality Critical makes the whole list unusable when this role finds nothing. Default Optional.
    fuer Pieces or categories this entry is meant for.
    stadtteil The ward this entry is meant for: Stadt, Burg, Vorstadt or Umland.
    chain Things in order; the first that exists is used.
    stuffChain Stuff in order. MapStone and MapWood take the stone or wood of the map.
    terrainChain, terrainMix Floors in order, or a weighted mix.
    roofChain Roofs in order.
    pawnChain Pawn kinds in order, for roles that place pawns.
    tagSearch Last resort: a thing with this building tag.

    When several entries of the same role fit a cell, the most specific wins: a fuer match beats a stadtteil match, which beats an entry without conditions. The cell's ward and the wall, tower and gatehouse pieces of that ward decide what matches.

    Ruins

    A RuinDef turns a generated settlement into a raided or destroyed one: breaches, burnt rooms, corpses, reduced loot. CBF uses ruins for quest sites. A ruin reaches a map either from a quest node or from a CustomBaseFramework.CBFOrtExtension on a SitePartDef. See Modding-Quests.

    CBF's shipped ruin inherits from the abstract CBF_Ruin_Basis, which only sets besatzung to Besatzer. Some fields are left out here:

    xml <CustomBaseFramework.RuinDef ParentName="CBF_Ruin_Basis"> <defName>CBF_Ruin_Ueberfallen</defName> <label>raided</label> <wandAbriss>0.15</wandAbriss> <haeufung>0.7</haeufung> <breschen>1~3</breschen> <torZerstoert>0.5</torZerstoert> <gebaeudeSchaden>0.1~0.5</gebaeudeSchaden> <feuer>0~3</feuer> <beuteFaktor>0.4</beuteFaktor> <beuteBeiBesatzern>0.5</beuteBeiBesatzern> <leichenBewohner>4~10</leichenBewohner> <leichenAngreifer>2~6</leichenAngreifer> <gefangene>0~3</gefangene> </CustomBaseFramework.RuinDef>

    Node Meaning
    angriffsseite Side the attack came from. Random if not set, unless the quest sets one.
    haeufung How strongly the damage gathers towards the attack side. 0 spreads it evenly. Default 0.6.
    breschen Number of breaches in the wall.
    torZerstoert Chance per gate to be destroyed.
    wandAbriss Chance scale for torn down walls.
    gebaeudeSchaden Share of hit points buildings lose.
    geschuetzeZerstoert Chance scale for destroyed turrets.
    brandstellen Chance scale for burnt out rooms.
    feuer Number of fires still burning.
    schutt Chance scale for rubble.
    felderVerwuestet Chance per crop plant to be destroyed.
    viehWeg Chance per animal to be gone.
    beuteFaktor Multiplier on the loot left in the settlement. Default 1.
    beuteBeiBesatzern Share of the loot moved to the occupiers.
    leichenBewohner, leichenAngreifer Corpses of residents and attackers.
    verwesungTage Age of the corpses in days.
    gefangene Residents held prisoner by the occupiers.
    besatzung Who holds the site: Keine, Bauherr (the builders) or Besatzer (occupiers). Default Besatzer. Prisoners only exist with Besatzer.
    besatzungAnteil Multiplier on the number of defenders. Default 1.

    Map steps

    KartenschritteDef lists vanilla or mod map generation steps that CBF skips on maps it builds itself. Only the def named CBF_Kartenschritte is read. To add steps, patch that def instead of writing a new one.

    xml <CustomBaseFramework.KartenschritteDef> <defName>CBF_Kartenschritte</defName> <unterdruecken> <li>Roads</li> <li>ScatterRuinsSimple</li> <li>AncientTurret</li> <li>DankPyon_BattlefieldRemains</li> </unterdruecken> <nurAbTechstufe> <li><schritt>SettlementPower</schritt><techstufe>Industrial</techstufe></li> </nurAbTechstufe> </CustomBaseFramework.KartenschritteDef>

    Node Meaning
    unterdruecken GenStepDef names skipped on CBF maps.
    nurAbTechstufe Steps that only run when the map's faction has at least this tech level. Each entry has schritt (GenStepDef name) and techstufe (default Industrial).

    The filter only applies to maps whose generator contains a CBF_ step. If CBF then builds nothing on the map, the skipped steps are run afterwards.

    A patch from your own mod:

    xml <Patch> <Operation Class="PatchOperationAdd"> <xpath>/Defs/CustomBaseFramework.KartenschritteDef[defName="CBF_Kartenschritte"]/unterdruecken</xpath> <value> <li>MyMod_ScatterCamps</li> </value> </Operation> </Patch>

    Buildability rules

    BaubarRegelDef is only read when the mod setting Make everything buildable is on. See Mod settings. The setting gives every building without an architect category one. The rules decide which category.

    xml <CustomBaseFramework.BaubarRegelDef> <defName>CBF_Baubar_Ruinen</defName> <rang>30</rang> <kategorie>CBF_RuinFurniture</kategorie> <kategorieLabel>Ruin Furn.</kategorieLabel> <ordnung>-102</ordnung> <dateiEnthaelt> <li>Buildings_Ruins</li> <li>Buildings_Ruined</li> </dateiEnthaelt> </CustomBaseFramework.BaubarRegelDef>

    Node Meaning
    dateiEnthaelt Parts of the XML file name the building was defined in. Case is ignored.
    kategorie DesignationCategoryDef to put matching buildings in. Created if it does not exist.
    kategorieLabel Label of the category when CBF creates it.
    ordnung Order of the created category in the architect menu.
    rang Rules are checked by rang, lowest first. The first match wins.

    Buildings that match no rule go into the category CBF_Baubar (label "CBF extra"). Buildings without build cost are skipped.

    Help texts

    HilfeDef holds the texts behind the help buttons in the editor. Each button asks for a fixed defName, for example CBF_Help_Wards.

    xml <CustomBaseFramework.HilfeDef> <defName>CBF_Help_Walls</defName> <label>Walls</label> <description>The wall pieces this ward is built from.</description> </CustomBaseFramework.HilfeDef>

    Node Meaning
    label, description Title and text of the help window.
    bilder Texture paths of images shown in the window.
    bildbreite Maximum image width. 0 uses the window width.

    A content mod does not need these. New HilfeDefs get no button. Translations go through DefInjected as usual.

    Dungeon profiles

    DungeonProfileDef exists in the code, but CBF ships none and nothing assigns one to a world object at the moment. Its fields are listed in DungeonProfileDef. Do not build content on it yet.

    How CBF takes over faction bases

    No patch is needed to make CBF build bases for a faction. CBF patches RimWorld so that a non-player faction settlement uses CBF's map generator CBF_Base_Faction when:

    • at least one usable settlement type matches the faction, or a type was assigned to this settlement by hand in the editor,
    • the faction is not switched off in the mod settings,
    • the settlement's WorldObjectDef has no map generator of its own,
    • the settlement is not in space,
    • no other mod's generator is known to take over this faction.

    CBF adds its world object comp to the vanilla Settlement and Site defs itself.

    Faction matching

    For each faction, CBF collects the settlement types in two groups:

    1. Own types. factionTags contains the faction's defName or its categoryTag.
    2. General types. fuerAlleFraktionen is true and techLevels contains the faction's tech level.

    Types that list the faction in excludeFactions are skipped. If the faction has any own types, only those are used. General types are only used for factions without own types. CBF's modern town, for example, sets fuerAlleFraktionen and the tech levels Industrial, Spacer and Ultra, so every such faction without own types gets it. A faction with no matching type keeps its vanilla base. Details of the plan fields are on Modding-Settlements.

    World icons

    A settlement type sets its world map icon with worldTexture:

    xml <worldTexture>World/WorldObjects/CBF/CBF_ModernTown</worldTexture>

    • The path is relative to Textures and has no file extension.
    • The icon is tinted in the faction colour.
    • It replaces the faction icon only for settlements CBF builds, and only if the faction is not switched off.
    • If the texture is missing, the faction icon stays and a warning is logged.

    CBF ships its icons in Textures/World/WorldObjects/CBF, for example CBF_City, CBF_MarketTown and CBF_Metropolis. Your own icons in the same folder of your mod show up in the editor's picker next to them.

    Tips

    • Load after CBF. Without it ParentName on CBF's abstract defs fails.
    • Draw a wall profile for every depth your settlement types use. The fallback to another depth works but logs a warning.
    • Towers need a square, odd size. Gatehouses need odd width and height.
    • Put MayRequire on every def or entry that names content from another mod, or move it into an IfModActive folder.
    • Check the log after loading. CBF reports broken references once per def and says what it does instead.
    • The full list of fields for every def type is in the Field reference.
