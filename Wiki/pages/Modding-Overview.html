Modding overview

Modding

This page is for modders who write XML for Custom Base Framework (CBF) by hand, or who want to understand what the in-game editor writes. It covers:

  • the folder layout of a content mod,
  • how the def types connect,
  • how supporting definitions configure wall profiles, materials, ruins, map steps, buildability rules and editor help,
  • how CBF takes over faction bases and draws world map icons.

Every field of every def type is listed in the Field reference. This page shows how the fields are used.

Your own content mod

A CBF content mod uses the normal RimWorld folder structure. New pieces, lists and plans can be defined entirely in XML. Use patches when changing definitions supplied by CBF or another mod.

Folder layout

MyCBFContent/
  About/
    About.xml
  LoadFolders.xml
  1.6/
    Defs/
      CustomBaseFramework/
        CustomBaseDefs/
          Buildings/
          WallParts/
        LootDefs/
        PawnKinds/
        PlanDefs/
        WallProfileDefs/
    Mods/
      MedievalOverhaul/
        Defs/
          CustomBaseFramework/
  Textures/
    World/
      WorldObjects/
        CBF/
          MyTown.png

Only About/About.xml and one Defs folder are required. The subfolder names under Defs are a convention. RimWorld reads every XML file under Defs, whatever the folder is called.

About.xml

The mod depends on CBF and loads after it:

<?xml version="1.0" encoding="utf-8"?>
<ModMetaData>
  <name>My CBF Content</name>
  <author>Me</author>
  <packageId>Me.MyCBFContent</packageId>
  <supportedVersions>
    <li>1.6</li>
  </supportedVersions>
  <modDependencies>
    <li>
      <packageId>EvilEyeGuy.CustomBaseFramework</packageId>
      <displayName>Custom Base Framework</displayName>
    </li>
  </modDependencies>
  <loadAfter>
    <li>EvilEyeGuy.CustomBaseFramework</li>
  </loadAfter>
  <description>Content for Custom Base Framework.</description>
</ModMetaData>

loadAfter matters. A def can only inherit with ParentName from a parent in a mod that loads earlier. CBF's abstract parents, such as CBF_Ruin_Basis, are only usable when your mod loads after CBF.

LoadFolders.xml for other mods

Content that needs another mod can go into a subfolder that only loads when that mod is active. CBF does this for Medieval Overhaul and Vanilla Factions Expanded - Medieval 2. Trimmed from CBF's own file:

<?xml version="1.0" encoding="utf-8"?>
<loadFolders>
  <v1.6>
    <li>/</li>
    <li>1.6</li>
    <li IfModActive="DankPyon.Medieval.Overhaul">1.6/Mods/MedievalOverhaul</li>
    <li IfModActive="OskarPotocki.VFE.Medieval2">1.6/Mods/VFEMedieval2</li>
  </v1.6>
</loadFolders>
  • / loads Textures and Languages from the mod root.
  • 1.6 loads 1.6/Defs and 1.6/Patches.
  • Each conditional line loads the Defs and Languages folders inside it. IfModActiveAll="a,b" loads a folder only when all listed mods are active.

MayRequire

For single defs or single list entries, RimWorld's MayRequire attribute is enough. On a def node it skips the whole def when the mod is missing. On a list item it skips only that item, for example a member of an object list:

<members>
  <li MayRequire="DankPyon.Medieval.Overhaul"><thing>DankPyon_RusticShelf</thing></li>
  <li><thing>Shelf</thing></li>
</members>

See Modding-Settlements for MayRequire on settlement types.

Texture files

World map icons go into Textures/World/WorldObjects/CBF/ of your mod. A settlement type names one in worldTexture. The editor lists every texture in that folder from all active mods. See World icons below.

What the editor writes for you

The in-game editor handles most of this. See Getting started.

  • A new mod created in the editor gets About/About.xml (dependency on CBF, loadAfter CBF) and these folders: 1.6/Defs/CustomBaseFramework/CustomBaseDefs/Buildings, .../WallParts, .../DungeonRooms, 1.6/Defs/CustomBaseFramework/Layouts, 1.6/Defs/CustomBaseFramework/LootDefs and 1.6/Patches.
  • When you save content that uses other mods, the editor adds those mods to About.xml.
  • When it saves a settlement type, it writes MayRequire on the def node for the mods the type needs.
  • If your mod already has a LoadFolders.xml with IfModActive lines, a new settlement type that needs one of those mods is saved into that mod's folder.

The editor does not write LoadFolders.xml and does not copy world icon images. Add those by hand.

XML values and a first test

Place complete definitions inside a <Defs> root. The examples that show only a field or <li> are fragments to insert into the surrounding definition, not standalone files. Use exact, case-sensitive field names and defName references rather than translated labels.

Ranges use minimum~maximum, for example <count>2~4</count>; a single number fixes the value. Write decimal values with a point in XML, even when the editor accepts a comma. A weight is relative to the other eligible entries: weights 3 and 1 give a 75%/25% split when those are the only candidates. A chance such as 0.75 is a separate probability check.

Start with one piece, one category and one small settlement plan. Load the content mod after CBF, check the log for unresolved references, then preview and generate the plan on a test map. An XML file can be well-formed while still naming unavailable definitions or producing a layout that cannot fit the terrain.

For changes to existing definitions, use XML patches. That guide works through CBF examples and explains how to target a single ward, list entry or anchor without replacing the rest of the definition.

Read the field tables

The first column gives the exact XML node name. A label shown below it is the editor wording, not another accepted XML name. For example, the editor's Pawn anchor is stored as <anchorKind>Spawn</anchorKind>.

Field type How to write it
Text or a Def reference Put the value between the field tags. Def references use defName, not the display label.
Whole number, number, true/false Use 3, 0.5, true or false, as appropriate.
IntRange or FloatRange Use a fixed value or min~max, such as 2~4.
Enum Use one of the exact listed words, including its spelling and capitalisation.
List of names Put each name in a separate <li> inside the field.
List of an embedded type Put that type's fields inside each <li>. Follow its reference link for the fields.
Embedded type Put its fields directly inside the named field, without a list wrapper.
Optional Omitting it leaves it unset, allowing the documented fallback or inheritance. Writing false or 0 is an explicit value.

The Default column describes a newly constructed object. It is not an instruction to write every field, and it may differ from the value used after inheritance or reference resolution. none means no initial value; do not write the word none into the XML. Some fields are required by later validation even though their initial value is empty.

Lists of Def references and lists of embedded records look different. For example, a plan's styles contains style names, while its wards contains records with kind, districts and other settings. The class name in a reference link tells you what data is expected; it does not replace the field name or the <li> tag.

How the defs connect

A settlement type (SettlementPlanDef) is the top of the tree. It is made of wards: rings such as the town, the suburb and the countryside. Each ward has districts: groups of buildings that stay together. A district asks for buildings by category or by single piece. A piece is one hand-drawn building. Its anchors are marked spots that CBF fills with objects, loot or pawns.

SettlementPlanDef (settlement type)
  worldTexture ............ world map icon
  materialList ............ MaterialListDef: walls, doors, roads the generator builds itself
  styles .................. StyleDef -> WallProfileDef
  techLevels, factionTags . which factions use it
  wards ................... rings from the middle outwards
    walls, gatehouses ..... wall pieces of this ring
    garrison .............. PawnListDef: defenders of this ring
    districts ............. building programme of the ring
      categories .......... PieceCategoryDef
        pieces ............ PieceDef
          anchors ......... object lists, LootTableDef, PawnListDef
  • Settlement types, wards and districts: Modding-Settlements
  • Pieces, categories and anchors: Modding-Pieces
  • Loot tables and loot containers: Modding-Loot
  • Pawn lists, garrisons and unit swap: Modding-Pawns
  • Quest sites and ruins in quests: Modding-Quests
  • Scenarios that start in a ruin: Modding-Scenarios

The rest of this page covers the def types on the side of that tree.

Wall profiles

A WallProfileDef describes a wall ring by its cross section. Each segment is a piece one cell wide or one cell high, drawn across the wall. The generator repeats the segments along the wall line. A profile can also name a tower piece and a gatehouse piece.

Example

From CBF's Medieval Overhaul folder:

<CustomBaseFramework.WallProfileDef>
  <defName>WallProfile_Stone_3</defName>
  <label>stone wall, drawn</label>
  <style>Standard</style>
  <depth>3</depth>
  <segments>
    <li>TownWall</li>
    <li>TownWall</li>
    <li>TownWall</li>
    <li>TownWall_Embrasure</li>
  </segments>
  <tower>Tower</tower>
  <gatehouse>CBF_MO_GateHouse_Small</gatehouse>
  <gatehouseOutward>West</gatehouseOutward>
</CustomBaseFramework.WallProfileDef>

<CustomBaseFramework.WallProfileDef>
  <defName>WallProfile_Palisade_1</defName>
  <label>palisade, drawn</label>
  <style>Rustical</style>
  <depth>1</depth>
  <segments>
    <li>Palisade</li>
  </segments>
  <tower>PalisadeTower</tower>
</CustomBaseFramework.WallProfileDef>

In the first profile, three plain wall segments follow one segment with an embrasure, so every fourth cross section of the wall has one.

Nodes

Node Meaning
style The style this profile belongs to. Used to find a profile for a settlement type.
depth Thickness of the wall ring in cells. Must be 1, 3 or 5. Default 3.
segments PieceDef names of the cross sections. Each piece must be 1 cell wide or 1 cell high, otherwise it is skipped with a warning. A segment shorter than depth leaves the missing columns empty.
tower PieceDef for towers on the wall. It sits on the centre line of the wall, so it must be square with an odd size. Otherwise it is ignored and the generator builds its own round tower.
gatehouse PieceDef placed with its centre on each gate. Both sides must be odd. Otherwise it is ignored and a plain gate is built.
gatehouseOutward The side of the drawn gatehouse piece that faces out of the settlement: North, East, South or West. Default South.
outwardIsLow Default orientation of segments. true means the south end of a vertical strip, or the west end of a horizontal strip, faces outwards. A segment piece that defines its outer side itself overrides this. Default true.
usable Set false to switch the profile off. CBF also sets it to false when no segment is valid.

A profile needs at least one segment, otherwise the def reports a config error.

How a profile is chosen

  1. The settlement type's styles are tried in order. For each style, its fallback chain is walked. The first usable profile with that style and the wanted depth wins.
  2. If none matches, the first usable profile with the wanted depth is taken. A warning is logged, and the material then comes from that profile's style.
  3. If no profile has that depth, the one with the nearest depth is taken. The wall of the material list fills the remaining columns.

A settlement type or a ward can also list its own wall pieces in walls. These replace the profile's segments. Tower, gatehouse and orientation still come from the chosen profile. See Modding-Settlements.

Styles

StyleDef

A style is only a name with an optional fallback:

<CustomBaseFramework.StyleDef>
  <defName>Standard</defName>
  <label>standard</label>
</CustomBaseFramework.StyleDef>

<CustomBaseFramework.StyleDef>
  <defName>Rustical</defName>
  <label>rustic</label>
  <fallback>Standard</fallback>
</CustomBaseFramework.StyleDef>

fallback is used when nothing is found for this style. The chain may not loop and may not be deeper than 16 steps.

What a style decides today

A style only picks the wall profile of a settlement type. It does not restrict which pieces are built.

Which factions use a settlement type is decided by factionTags and techLevels on the SettlementPlanDef, not by the style. See How CBF takes over faction bases.

A settlement type lists its styles in order:

<styles>
  <li>Rustical</li>
  <li>Standard</li>
</styles>

The older single field style still loads. If styles is empty, style is used as its only entry.

Material lists

The generator builds some things itself instead of taking them from pieces: walls, doors, gates, fences, roads, bridges, roofs and so on. Each of these parts is a role, for example WALL or FLOOR_ROAD. A MaterialListDef says which thing, stuff or floor each role uses. Every settlement type must name one in materialList. There is no hidden default: a settlement type without a material list is switched off. The editor has its own part for material lists, see Material lists.

Trimmed from the shipped base list:

<CustomBaseFramework.MaterialListDef>
  <defName>CBF_MaterialList_Base</defName>
  <label>base</label>
  <roles>
    <li>
      <role>WALL</role>
      <criticality>Critical</criticality>
      <chain>
        <li MayRequire="DankPyon.Medieval.Overhaul">DankPyon_CastleWall</li>
        <li>Wall</li>
      </chain>
      <stuffChain><li>MapStone</li><li>BlocksGranite</li><li>WoodLog</li></stuffChain>
      <tagSearch>AnyWall</tagSearch>
    </li>
    <li>
      <role>BRIDGE</role>
      <terrainChain><li>Bridge</li></terrainChain>
    </li>
  </roles>
</CustomBaseFramework.MaterialListDef>

A list for your own mod usually inherits from the base list and only overrides what differs. This example is not shipped. It gives palisade walls and palisade towers a rustic door, and gives the countryside packed dirt roads:

<CustomBaseFramework.MaterialListDef>
  <defName>MyMod_Materials</defName>
  <label>my mod</label>
  <parent>CBF_MaterialList_Base</parent>
  <roles>
    <li>
      <role>DOOR</role>
      <forPieces><li>Palisade</li><li>CBF_MO_PalisadeTower</li></forPieces>
      <chain><li MayRequire="DankPyon.Medieval.Overhaul">DankPyon_RusticDoor</li><li>Door</li></chain>
      <stuffChain><li>WoodLog</li></stuffChain>
    </li>
    <li>
      <role>FLOOR_ROAD</role>
      <district>Rural</district>
      <terrainChain><li>PackedDirt</li></terrainChain>
    </li>
  </roles>
</CustomBaseFramework.MaterialListDef>
Node What it does
parent Another material list. A role this list does not define, or defines only for other pieces or wards, is taken from the parent.
roles One entry per role and condition.
role The role name, such as WALL, DOOR, GATE, FENCE, FLOOR_ROAD, BRIDGE, ROOF.
criticality Critical marks the whole list as unusable when this role finds nothing. CBF logs a config error and the editor shows a warning. Default Optional.
forPieces Pieces or categories this entry is meant for.
district The ward this entry is meant for: Town, Suburb or Rural.
chain Things in order. The first that exists is used.
stuffChain Stuff in order. MapStone and MapWood take the stone or wood of the map.
terrainChain, terrainMix Floors in order, or a weighted mix.
roofChain Roofs in order.
pawnChain Pawn kinds in order, for roles that place pawns.
tagSearch Last resort: a thing with this building tag.

When several entries of the same role fit a cell, the most specific wins. A forPieces match beats a district match, which beats an entry without conditions. What matches depends on the cell's ward and on the wall, tower and gatehouse pieces of that ward.

Ruins

A RuinDef turns a generated settlement into a raided or destroyed one: breaches, burnt rooms, corpses, reduced loot. CBF uses ruins for quest sites and for scenarios that start in a ruin. On a quest site a ruin reaches the map either from a quest node or from a CustomBaseFramework.CBFSiteExtension on a SitePartDef, see Modding-Quests. For scenarios see Starting in a ruin.

CBF's shipped ruin inherits from the abstract CBF_Ruin_Basis, which only sets occupation to Occupier. Some fields are left out here:

<CustomBaseFramework.RuinDef ParentName="CBF_Ruin_Basis">
  <defName>CBF_Ruin_Raided</defName>
  <label>raided</label>
  <wallDemolition>0.15</wallDemolition>
  <clustering>0.7</clustering>
  <breaches>1~3</breaches>
  <gateDestroyed>0.5</gateDestroyed>
  <buildingDamage>0.1~0.5</buildingDamage>
  <fires>0~3</fires>
  <lootFactor>0.4</lootFactor>
  <lootWithOccupiers>0.5</lootWithOccupiers>
  <residentCorpses>4~10</residentCorpses>
  <attackerCorpses>2~6</attackerCorpses>
  <prisoners>0~3</prisoners>
</CustomBaseFramework.RuinDef>
Node Meaning
attackSide Side the attack came from. Random if not set, unless the quest sets one.
clustering How strongly the damage gathers towards the attack side. 0 spreads it evenly. Default 0.6.
breaches Number of breaches in the wall.
gateDestroyed Chance per gate to be destroyed.
wallDemolition Chance scale for torn down walls.
buildingDamage Share of hit points buildings lose.
turretsDestroyed Chance scale for destroyed turrets.
burnMarks Chance scale for burnt out rooms.
fires Number of fires still burning.
rubble Chance scale for rubble.
fieldsRavaged Chance per crop plant to be destroyed.
livestockGone Chance per animal to be gone.
lootFactor Multiplier on the loot left in the settlement. Default 1.
lootWithOccupiers Share of the loot moved to the occupiers.
residentCorpses, attackerCorpses Corpses of residents and attackers.
rotDays Age of the corpses in days.
prisoners Residents held prisoner by the occupiers.
occupation Who holds the site: None, Builder (the faction that built it) or Occupier (the attackers). Default Occupier. Prisoners only exist with Occupier.
occupationChance Multiplier on the number of defenders. Default 1.

Map steps

A map is generated in steps (GenStepDefs), for example roads or scattered ruins. Some vanilla or mod steps would clutter a CBF settlement. MapStepsDef lists the steps CBF skips on maps it builds itself. Only the def named CBF_MapSteps is read. To add steps, patch that def instead of writing a new one.

Trimmed from the shipped def:

<CustomBaseFramework.MapStepsDef>
  <defName>CBF_MapSteps</defName>
  <suppress>
    <li>Roads</li>
    <li>ScatterRuinsSimple</li>
    <li>AncientTurret</li>
    <li>DankPyon_BattlefieldRemains</li>
  </suppress>
  <fromTechLevel>
    <li><step>SettlementPower</step><techLevel>Industrial</techLevel></li>
  </fromTechLevel>
</CustomBaseFramework.MapStepsDef>
Node Meaning
suppress GenStepDef names skipped on CBF maps.
fromTechLevel Steps that only run when the map's faction has at least this tech level. Each entry has step (GenStepDef name) and techLevel (default Industrial).

The filter only applies to maps whose generator contains a step whose name starts with CBF_. If CBF then builds nothing on the map, the skipped steps are run afterwards.

A patch from your own mod:

<Patch>
  <Operation Class="PatchOperationAdd">
    <xpath>/Defs/CustomBaseFramework.MapStepsDef[defName="CBF_MapSteps"]/suppress</xpath>
    <value>
      <li>MyMod_ScatterCamps</li>
    </value>
  </Operation>
</Patch>

Buildability rules

Many buildings in RimWorld and in mods have no place in the architect menu, so players cannot build them. The mod setting Make everything buildable (building aid) gives each of them a menu category. See Mod settings. BuildableRuleDef decides which category a building gets. The rules are only read when the setting is on.

<CustomBaseFramework.BuildableRuleDef>
  <defName>CBF_Buildable_Ruins</defName>
  <rank>30</rank>
  <category>CBF_RuinFurniture</category>
  <categoryLabel>Ruin Furn.</categoryLabel>
  <order>-102</order>
  <fileContains>
    <li>Buildings_Ruins</li>
    <li>Buildings_Ruined</li>
  </fileContains>
</CustomBaseFramework.BuildableRuleDef>
Node Meaning
fileContains Parts of the XML file name the building was defined in. Case is ignored.
category DesignationCategoryDef to put matching buildings in. Created if it does not exist.
categoryLabel Label of the category when CBF creates it.
order Order of the created category in the architect menu.
rank Rules are checked by rank, lowest first. The first match wins.

Buildings that match no rule go into the category CBF_Baubar (label "CBF extra"). Buildings without build cost are skipped.

Help texts

HelpDef holds the texts behind the help buttons in the editor. Each button asks for a fixed defName, for example CBF_Help_Wards.

<CustomBaseFramework.HelpDef>
  <defName>CBF_Help_Walls</defName>
  <label>Walls</label>
  <description>The wall pieces this ward is built from.</description>
</CustomBaseFramework.HelpDef>
Node Meaning
label, description Title and text of the help window.
images Texture paths of images shown in the window.
imageWidth Maximum image width. 0 uses the window width.

A content mod does not need these. A new HelpDef with a defName no button asks for is never shown. Translations go through DefInjected as usual.

Dungeon profiles

DungeonProfileDef is an older profile type. The current development workflow uses a SettlementPlanDef with kind set to Dungeon and an ordered levels list. See Dungeon levels for the implemented structure, the separate development content and fields that are not yet connected to generation.

How CBF takes over faction bases

No patch is needed to make CBF build bases for a faction. CBF patches RimWorld so that a non-player faction settlement uses CBF's map generator CBF_Base_Faction when all of these hold:

  • at least one usable settlement type matches the faction, or a type was assigned to this settlement by hand in the editor. Camp types and A Rim of Ice and Fire holding types (plans with campTypes or riafHolding) do not count here,
  • the faction is not switched off in the mod settings,
  • the settlement's WorldObjectDef has no map generator of its own,
  • the settlement is not in space,
  • no other mod's generator is known to take over this faction,
  • with World Domination 2.0: if the settlement has a World Domination tier, at least one matching type has a wdLevel.

CBF adds its world object comp to the vanilla Settlement and Site defs itself.

Faction matching

For each faction, CBF collects the settlement types in two groups:

  1. Own types. factionTags contains the faction's defName or its categoryTag.
  2. General types. forAllFactions is true and techLevels contains the faction's tech level.

Types that list the faction in excludeFactions are skipped. If the faction has any own types, only those are used. General types are only used for factions without own types.

For example, CBF's modern town sets forAllFactions and the tech levels Industrial, Spacer and Ultra. Every such faction without own types gets it. A faction with no matching type keeps its vanilla base. The full picking order is on Modding-Settlements.

World icons

A settlement type sets its world map icon with worldTexture:

<worldTexture>World/WorldObjects/CBF/CBF_ModernTown</worldTexture>
  • The path is relative to Textures and has no file extension.
  • The icon is tinted in the faction colour.
  • It replaces the faction icon only for settlements CBF builds, and only if the faction is not switched off.
  • If the texture is missing, the faction icon stays and a warning is logged.

CBF ships its icons in Textures/World/WorldObjects/CBF, for example CBF_City, CBF_MarketTown and CBF_Metropolis. Your own icons in the same folder of your mod show up in the editor's picker next to them.

Tips

  • Load after CBF. Without it, ParentName on CBF's abstract defs fails.
  • Draw a wall profile for every depth your settlement types use. The fallback to another depth works but logs a warning.
  • Towers need a square, odd size. Gatehouses need odd width and height.
  • Put MayRequire on every def or entry that names content from another mod, or move it into an IfModActive folder.
  • Check the log after loading. CBF reports broken references once per def and says what it does instead.
  • The full list of fields for every def type is in the Field reference.
