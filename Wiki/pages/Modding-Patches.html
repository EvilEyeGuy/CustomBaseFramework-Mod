Changing existing content with XML patches

Modding

Use a patch when you want to change a building, settlement plan or loot table supplied by another mod. For example, you can give the modern village a larger garrison without copying its houses, roads and other settings. Updates to those untouched parts will still reach your game.

To create an independent settlement instead, give a new SettlementPlanDef its own defName. See Your own content mod for the folder layout and dependencies. A second definition with an existing defName is not a patch.

Where the file goes

Create your own local content mod and load it after CBF and any other mod you are changing. In a mod with a loaded 1.6 folder, save the examples below under 1.6/Patches/. A patch file has a <Patch> root; new definitions belong under Defs/ with a <Defs> root.

The editor can produce patches too: edit supported content from another mod and choose Save as patch. Keep your hand-written patches outside its Patches/CBF_Changes/ folder. Saving that definition again in the editor rewrites its generated patch file.

Restart RimWorld after changing XML by hand, then test a newly generated settlement. An existing map already contains its buildings and pawns; a patch does not rebuild them.

Find the definition and the field

Find the defName in the source XML or the editor. Use this internal name, not the translated label shown to players. Then follow the XML nesting to the value you want to change.

This excerpt is from the shipped CBF_Plan_ModernVillage plan:

<wards>
  <li>
    <kind>Town</kind>
    <garrison>
      <li>
        <list>CBF_Modern_Garrison_Inside</list>
        <count>6~9</count>
        <post>Inside</post>
      </li>
    </garrison>
  </li>
</wards>

Each li is one list entry. The first belongs to wards; the second belongs to that ward's garrison. The field reference calls those embedded types Stadtteil and Garnisonseintrag. Those class names explain the data structure; they are not extra XML tags to insert.

The XPath for this count is:

Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_ModernVillage"]/wards/li[kind="Town"]/garrison/li[list="CBF_Modern_Garrison_Inside"]/count

Read it from left to right: find the plan, its Town ward, the garrison entry using the named pawn list, and finally that entry's count. Conditions in square brackets select matching nodes. Prefer these names to positions such as li[1], which may point to a different entry after an update.

Replace an existing value

This complete patch changes the Town garrison from 6~9 to 10~14:

<Patch>
  <Operation Class="PatchOperationReplace">
    <xpath>Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_ModernVillage"]/wards/li[kind="Town"]/garrison/li[list="CBF_Modern_Garrison_Inside"]/count</xpath>
    <value>
      <count>10~14</count>
    </value>
  </Operation>
</Patch>

Replace replaces the selected node itself, so value includes the <count> tag. It changes this garrison entry only. The countryside's garrison and pawns spawned by buildings are additional inhabitants, so 10–14 is not the settlement's total pawn count.

The target must exist in the loaded XML. A C# default shown in the field reference does not create an XML node for a patch to select.

Add a field that may be absent

Use PatchOperationAdd on the parent when the field is absent. Adding a second copy of a field that already exists can cause loading problems. A conditional operation handles both cases.

This patch sets the existing small house's wall preference. If it has no placement block, the patch creates it. If placement exists, it adds or replaces only atWall:

<Patch>
  <Operation Class="PatchOperationConditional">
    <xpath>Defs/CustomBaseFramework.PieceDef[defName="CBF_Vanilla_Dwelling_Small_A"]/placement</xpath>
    <match Class="PatchOperationConditional">
      <xpath>Defs/CustomBaseFramework.PieceDef[defName="CBF_Vanilla_Dwelling_Small_A"]/placement/atWall</xpath>
      <match Class="PatchOperationReplace">
        <xpath>Defs/CustomBaseFramework.PieceDef[defName="CBF_Vanilla_Dwelling_Small_A"]/placement/atWall</xpath>
        <value><atWall>Preferred</atWall></value>
      </match>
      <nomatch Class="PatchOperationAdd">
        <xpath>Defs/CustomBaseFramework.PieceDef[defName="CBF_Vanilla_Dwelling_Small_A"]/placement</xpath>
        <value><atWall>Preferred</atWall></value>
      </nomatch>
    </match>
    <nomatch Class="PatchOperationAdd">
      <xpath>Defs/CustomBaseFramework.PieceDef[defName="CBF_Vanilla_Dwelling_Small_A"]</xpath>
      <value><placement><atWall>Preferred</atWall></placement></value>
    </nomatch>
  </Operation>
</Patch>

The house may now favour a town wall when the plan has one; it remains eligible elsewhere. Required would demand wall contact and is unsuitable for a design that must also work in open towns. See Placement rules.

Add or remove a list entry

To give the village another building request, select its entries container and add one li. This example uses a tavern category already available in CBF and requests one additional tavern:

<Patch>
  <Operation Class="PatchOperationAdd">
    <xpath>Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_ModernVillage"]/wards/li[kind="Town"]/districts/li[name="VillageCore"]/entries</xpath>
    <value>
      <li><tag>CBF_Vanilla_Tavern</tag><count>1</count></li>
    </value>
  </Operation>
</Patch>

The plan already has a CBF_Vanilla_Tavern entry requesting 0~1. Adding this example leaves that request in place. To change the original quantity instead, replace its count using entries/li[tag="CBF_Vanilla_Tavern"]/count. Requested buildings still need enough room to be placed.

To remove the original tavern request, use this alternative patch:

<Patch>
  <Operation Class="PatchOperationRemove">
    <xpath>Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_ModernVillage"]/wards/li[kind="Town"]/districts/li[name="VillageCore"]/entries/li[tag="CBF_Vanilla_Tavern"]</xpath>
  </Operation>
</Patch>

Remove has no value. An XPath can match several nodes: after applying the Add example above, this Remove example would remove both matching tavern entries. Test each example separately unless you intend to combine their effects.

Choose how widely a change should apply

What you change Who uses the result
A plan's district entry That request in that settlement plan
A piece's anchor Every use of that anchor in the piece
An object-list member's lootTable That selected member wherever the shared list is used; it overrides the anchor's table
A shared loot table Every container or nested table that resolves it
A category's placement rules Eligible pieces using that category, subject to their own overrides and inheritance
A material list Plans using the list, plus child lists where the role is inherited

For example, to change one house's kitchen goods, create a new loot table with your own defName and point that house's Fill anchor to it. Changing the shared kitchen table would affect other buildings too. Locate the anchor with legend/li[anchor="Kitchen"]; the symbol used to draw its cells can differ between pieces.

Optional mods and inheritance

If your patch only applies when another mod is active, add its package ID as MayRequire on the operation. For an MO-only operation, for example:

<Operation Class="PatchOperationConditional" MayRequire="DankPyon.Medieval.Overhaul">
  <xpath>Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_Village_New"]/mapSize</xpath>
  <match Class="PatchOperationReplace">
    <xpath>Defs/CustomBaseFramework.SettlementPlanDef[defName="CBF_Plan_Village_New"]/mapSize</xpath>
    <value><mapSize>225</mapSize></value>
  </match>
</Operation>

Put this operation inside a <Patch> root. It does nothing when MO is absent or the selected node is absent. That is useful for an optional integration, but it can also hide a misspelled XPath. During development, confirm that your intended target exists.

There are two different kinds of inheritance:

  • RimWorld's Name, ParentName and Abstract attributes combine XML definitions. Patch operations address XML nodes; do not assume a field inherited from an abstract parent is physically written on the child. Inspect the parent and child. Changing the parent can affect every child.
  • CBF's <parent> fields link categories or material lists by defName at runtime. Removing a local override can make the parent value apply again. An empty category list may also fall back to a parent; it does not necessarily mean “allow nothing”.

Check the result

  1. Restart with your patch mod enabled and loaded after its targets. Check the log for failed patch operations and unresolved def names.
  2. Open the affected plan, piece or table in the editor. Confirm that the stored setting changed, rather than judging only from a random result.
  3. Generate a fresh example on a test map. For changes to selection chances or weights, try several seeds.
  4. Check the feature in use: open the container, inspect the defenders, or walk through the altered building. A correct preview cannot verify every in-game interaction.
Symptom Check
Patch operation failed Wrong defName, wrong nesting, absent node, or target mod not loaded
Nothing changes after restarting Conditional operation skipped, later patch overwrote the value, or you inspected an existing map
Too many entries changed XPath selected more than one li; add a ward, district or entry condition
Building does not appear Plan eligibility, category membership, mod requirements and available space
Loot differs from your table Member override, foreign/lootForeign, empty-list mode, or World Domination integration

Use the field reference to check accepted fields and values, and the feature guides for their effects. XML syntax alone cannot tell you whether a building fits or which reference wins.
