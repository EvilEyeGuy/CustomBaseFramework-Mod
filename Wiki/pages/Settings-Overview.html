What you can change

Start

Use this page to distinguish editable settings from fixed XML identifiers. The tables map editor controls to their stored values, while the final section explains how changes to another mod are saved as patches. The field reference documents individual fields and defaults.

Values in XML are case-sensitive. They are the names the code uses, so the editor sometimes shows a different label for the same value. Where that is the case, the editor label is given in bold.

Labels, counts, weights, chances, distances and radii are ordinary tuning values. Keep them within the documented ranges and check the editor’s validation messages. Large counts, sizes or spacing requirements can still prevent a plan from fitting, so preview the result after substantial changes.

Values with a fixed meaning

These fields only accept certain words. Anything else is an error or is ignored.

Ward kind (kind)

A ward is one ring of a settlement. Every settlement type has up to three. The kind decides which ring a ward is:

Kind Editor tab Ring Gap between buildings (buildingGap) Clears plants (clearRubble)
Town Town Innermost, protected best, filled first 1 to 2 yes
Suburb Suburb Around the town 3 to 5 no
Rural Countryside Outside, farmsteads and pens 4 to 8 no

The last two columns are the values a ward gets when the editor creates it. In hand-written XML, buildingGap 0 to 0 takes the gap of the settlement type, and clearRubble is true unless set.

  • The kind is the identity of a ward. A settlement type has at most one ward of each kind. That is why the editor shows each ward as a fixed tab and does not let you change its kind.
  • A missing ward is added with + next to the ward tabs. You cannot add a second ward of the same kind. In XML a second one gets no area.
  • A walled settlement type needs a Town ward. Without one the plan fails. Without a Suburb there is simply no suburb.
  • Fields work in the suburb and the countryside, pens only in the countryside.
  • Castle exists in the code but is not planned as a ring of its own. Do not use it.
  • The name of a ward is replaced when the game loads. Use label for your own display name.

Kind of place (kind)

Set on the settlement type as Kind of place.

Kind What changes
MedievalTown Walls with towers and gatehouses. The default.
ModernTown Street grid with roads up to 6 wide, power conduits, no gatehouses, wards without walls allowed, fields not fenced.
Camp Like a modern town, but without drawn roads. Only used for the quest sites listed under Camp types (campTypes), never for normal settlements.

Dungeon uses the development levels workflow. Its example content is a separate development mod; see Dungeon levels.

Garrison post (post)

Where the pawns of a garrison entry stand.

Post Editor label Where the pawns stand
Inside Inside On lanes, squares and open ground inside the ward
Walkway Wall On the wall walk at the embrasures
Gate Gate At the gates

If a post has no cells, for example a ward without a wall walk, the pawns stand inside instead.

Pawn list role (role)

How the pawns of a pawn list behave.

Role Editor label Behaviour
Guard Guard Joins the defence of the settlement.
Sentry Post Holds its spot around the anchor.
Gunner Gunner Mans the guns around its spot.
Civilian Civilian May flee and does not need to be able to fight. The default. The log warns when a civilian list contains fighters.

Anchors

An anchor is a marked cell in a piece where CBF places something when the piece is built. The anchor kind decides what:

Kind Does
Connect Ties the piece to its surroundings, see the names below
Fill Places objects and fills them with loot
Object Places objects, or an ideoligion building
Spawn Places pawns

Anchor names are free labels, except these four:

Name Meaning
Wall The town wall docks here. Gatehouses need at least two cells.
Outside The side that faces out. It gives the piece its direction.
Annex Annexes attach here, see Annexes
Water Water cells of harbor pieces

Material lists

A material list says which thing fills each role, for example which wall or door. See Material lists.

  • criticality: Optional or Critical. If a critical role finds nothing, the whole list is unusable, and with it every settlement type that uses it.
  • stuffChain knows two special words: MapStone (stone blocks of the map, Stone of the map) and MapWood (wood, Wood of the map).
  • district: Town, Suburb or Rural.
  • Roles the generator uses itself: WALL, DOOR, GATE, FLOOR_ROAD, FENCE, FENCE_GATE, PEN_MARKER, BRIDGE, ROOF, CONDUIT and the others shown in the list. Other role names work in pieces as long as the list defines them.
  • Applies to and the ward choice (Any ward by default) use the cell's ward context during settlement generation. They also affect roles inside pieces. A concrete thing or terrain drawn into a piece does not use that role lookup. A standalone piece preview may lack the ward context needed for conditional rows.

Do not change

Other content, the code or savegames refer to these names. Renaming or deleting them breaks something.

  • defNames of settlement types in use. Savegames store the settlement type of each settlement by name. A renamed type loads with a warning, and the settlement gets a different type.
  • District names within a settlement type. Fields and pens belong to their district by name, and names must be unique in the whole plan.
  • Shared material lists: CBF_MaterialList_Base, CBF_MO_MaterialList, CBF_Modern_MaterialList, CBF_VFEM2_MaterialList. Most shipped settlement types use them.
  • Abstract parents: CBF_BeutebehaelterBase, CBF_Ruin_Basis, CBF_Modern_SoldatBasis, CBF_MO_NeutralerSoldatBasis, CBF_MO_StammBasis. Inherit from them, do not change them.
  • Categories the generator looks for by name: WallTower, WallGateHouse, GateHouse, WallSegment, CBF_ModernDefense, CBF_Vanilla_Gatehouse, Market, Farm, Landmark, HouseSmall, DungeonRoom.
  • Defs the code looks up: CBF_EmptyCell, CBF_MapSteps, CBF_Base_Faction, CBF_Terrain, CBF_Hold, CBF_Walkway, CBF_Editor.
  • The prefix CBF_ on map generators and map steps marks a map as a CBF settlement, and the uninstaller removes every CBF_ def. Do not give defs of your own mod this prefix; use your own.
  • Styles Standard, Rustical, Fancy, CBF_Medieval, CBF_VFEM2, CBF_ModernVanilla: many pieces refer to them.
  • packageIds in LoadFolders.xml of other mods: they decide which content folders load.

Changing content of other mods

You can change settlement types, pieces, categories, loot tables, object lists, crop lists, material lists and pawn lists of CBF or of other mods. The original files stay untouched. When you save, the editor writes a patch into your own mod: Patches/CBF_Changes/<type>_<defName>.xml in the version folder of your mod.

  • The editor compares your changes with the source and writes operations for changed fields and list entries. This preserves unrelated fields, but patches can still conflict if another mod changes the same target. Check the load order and inspect the result after restarting.
  • Every operation only runs when the mod it patches is active (MayRequire). For content that CBF or another mod only loads together with a further mod, such as the Medieval Overhaul settlement types, that mod is required too.
  • Every operation also checks first that its target exists. If a mod renames or removes something, the operation does nothing instead of causing errors.
  • Saving again rewrites the patch file for that def from the current state. To return to the source version, remove that generated patch file and restart. Other active mods may still patch the same definition.
  • Renaming and deleting defs of other mods is not possible, because other content and savegames refer to their names. Use Copy into my mod or Duplicate for an independent version under a new name.
  • Changing the structure of a piece of another mod (exporting it again from the map) is also saved as a patch. The new structure takes effect after restarting the game.

Your mod has to load after the mod it patches. The editor adds this to your About.xml. For hand-written changes, see Changing existing content with XML patches, including examples for replacing values, adding missing fields and selecting list entries.
